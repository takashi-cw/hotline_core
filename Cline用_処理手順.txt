【モード宣言】

ユーザーの指示文言によって実施するフェーズが変わる。

  "事前調査して"  → 【調査フェーズ】のみ実施。コードは一切変更しない。
  "着手して"      → 【実装フェーズ】を実施（調査済みの場合はスキップ可）
  "続けて"        → 前回の続きから【実装フェーズ】を再開

【調査フェーズ】― コード変更なし。結果を報告して止まる。

A. 影響ファイル一覧を列挙する
B. 依存関係と影響範囲を文章で説明する
C. 変更方針を3行で要約する
D. 処理規模の目安（小/中/大）と、何回の応答に分かれるかを概算する
E. ライセンス・依存チェーンの確認
   - 新たに import するパッケージやモジュールがある場合、そのライセンスを明示すること
   - 判断基準：「このコードを含むプロジェクトを MIT で配布できるか？」に Yes と言えること
F. 調査結果を ROADMAP.md に記録するかユーザーに確認する
→ ここで止まる。ユーザーから "着手して" が来るまでコードを触らない。

【実装フェーズ】― 処理時の注意事項：推奨順

1. 処理規模の目安（小/中/大）と、何回の応答に分かれるか教えて
2. 変更前に、今回触るファイル一覧を先に出して
3. 影響を受ける箇所を列挙して
4. 依存関係を文章で説明して
5. 変更方針を3行で要約して
6. ライセンス・依存チェーンの確認
   - 新たに import するパッケージやモジュールがある場合、そのライセンスを明示すること
   - 間接依存（A→B→C）の末端まで確認し、GPL/AGPL/商用制限付きライセンスが含まれていないか報告すること
   - 既存コードから別ライブラリのコードをコピーまたは参考にした場合、その出典とライセンスを明示すること
   - 判断基準：「このコードを含むプロジェクトを MIT で配布できるか？」にYes と言えること
7. フォルダ構成を機能別に分けること
   - 規模に関わらず、以下の観点でフォルダ分けを提案すること
       計算・変換ロジック  → src/core/  または  src/lib/
       UI・表示            → src/ui/    または  src/components/
       ユーティリティ      → src/utils/
       エントリポイント    → src/ 直下  または  プロジェクトルート
   - 実装前にフォルダ構成案をユーザーに提示し、承認を得てから作成すること
   - 既存プロジェクトで構成変更を伴う場合は、変更前後の差分を明示すること
   - 判断基準：「このフォルダを別プロジェクトにそのままコピーして意味が通るか？」に Yes と言えること
8. 疎結合・単一責務を守ること
   - モジュール間は疎結合にすること（密結合にしない）
   - 1つの関数・クラスには1つの責務のみ（単一責務の原則）
   - 関数間の依存は引数と戻り値で明示し、グローバル変数や暗黙の状態共有で繋がない
   - 取得（データソース）と処理（計算ロジック）と出力（表示・保存）は分離すること
   - 複数の出力先（メニュー・画面等）が同じ計算を必要とする場合、計算は1箇所に集約し、出力側は結果を参照するだけにすること
   - 外部ライブラリの呼び出し元を集約すること。同じライブラリを複数箇所から直接呼ばず、1つのエンジン層に限定し、他のコードはエンジン層経由で利用すること
   - 判断基準：「この関数/モジュールを別プロジェクトにコピーして、単体で動くか？」に Yes と言えること
9. 副作用のない関数を作る、副作用を隔離する
   - 計算・変換ロジックは純粋関数にすること
     （引数だけを使い、値を返すだけ。ファイルI/O・DB接続・グローバル変数の変更・print を含めない）
   - 副作用（ファイル書き出し・API呼び出し・画面出力等）は呼び出し元に集約すること
   - 1つの関数に「計算」と「保存」を混ぜないこと
   - 判断基準：その関数を同じ引数で100回呼んで、毎回同じ結果が返るなら
     純粋関数。そうでなければ副作用が混ざっている
10. パスを絶対パスでハードコードしないこと
    - ディレクトリパスやファイルパスに絶対パス（/Users/xxx/... 等）を直接書き込まないこと
    - __file__ からの相対パス、os.path、pathlib.Path 等で動的に解決すること
    - sys.path.insert にプロジェクト固有の絶対パスを入れないこと
    - 判断基準：「このコードを別のマシン・別のユーザーがクローンして、パスの書き換えなしに動くか？」に Yes と言えること
11. 一括生成せず、1ファイルずつ出して
12. ツール呼び出しは並列処理せず、直列処理（1つずつ順番に実行）すること
    - 複数のファイル編集・検索・コマンド実行を同時に走らせない
    - 前の処理が完了してから次の処理を開始すること
13. CLIコマンドはブロッキングしない形式で実行すること
    - シェルのヒアドキュメント（<< 'EOF' ... EOF）は使用しないこと
      → ツール経由では EOF 終端が正しく渡されずプロセスがブロックし、
        VSCode ごとフリーズする原因になる
    - Node.js のインライン実行は node -e "..." を使うこと
    - Python のインライン実行は python3 -c "..." を使うこと
    - 長いスクリプトが必要な場合は、一時ファイル（例：_test_runner.js）に
      write_to_file で書き出してから node _test_runner.js で実行すること
    - バックグラウンド実行（& や nohup）も結果が返らなくなるため使用しないこと
    - 実行時間が数秒以上かかる可能性があるコマンド（サーバー起動・watch系等）は
      即時終了しないため使用しないこと。必要な場合はユーザーに手動実行を依頼すること
    - 判断基準：「このコマンドは結果を返して即終了するか？」に Yes と言えること
14. 単体テストを必ず実施し、結果を毎回報告して
    - 純粋関数は単体テスト（入力→出力の assert）で検証すること
    - 副作用を含む関数は結合テストとして分けて報告すること
15. 作業が完了したら、該当するドキュメントに作業の内容を追記しすること。
    - 更新日付はユーザーに確認すること

【Cline固有の操作ルール】

P-1. PlanとActは別タスクとして扱うこと
     - Plan（調査・設計）とAct（実装）は明確に分けること
     - Plan後、ユーザーの "着手して" を受けてからActに移行すること
     - Plan内容が空・未確定のままActを開始しないこと

P-2. ファイル置換後は必ず全文を確認すること
     - replace_in_file を実行したら、返却された final_file_content を必ず確認すること
     - 番号重複・意図しない削除・文字化けがないか目視チェックすること
     - 複数箇所を置換する場合は1箇所ずつ確認してから次に進むこと
     - 大規模な変更や番号の振り直しが必要な場合は replace_in_file の連打を避け、
       write_to_file で全文を書き直すこと
     - 判断基準：「置換後の全文を読んで、意図通りか？」に Yes と言えること

P-3. CLIコマンドが応答しない場合の対処
     - コマンドが返ってこない場合は「入力待ち状態」を疑うこと
     - ヒアドキュメント・対話型コマンド・バックグラウンド実行が原因のことが多い
     - 対処：コマンドを中断し、node -e "..." 等の即時終了形式に切り替えること
     （※ 予防策は 13番を参照）

P-4. Act開始前に git 管理状況を確認すること
     - git status でコミット済みか確認し、未コミットの変更がある場合はユーザーに報告すること
     - git 管理外のプロジェクトの場合のみ「バックアップを推奨」と一言添えること
     - バックアップの実施はユーザーの判断に委ねること（強制しない）

P-5. 失敗経験は処理手順書へ圧縮して引き継ぐこと
     - 同じタスク内で発生した失敗は、その場で原因を分析すること
     - 分析後、「失敗内容・原因・再発防止ルール」を3行以内で要約すること
     - 次回以降の作業に必要な内容は、処理手順書へ追記候補として提示すること（タスク完了時または失敗直後に行う）
     - 長い失敗ログや会話履歴を次タスクへ持ち越さず、要約済みルールだけを引き継ぐこと
     - 判断基準：「この失敗を知らない新しいタスクでも、同じ事故を避けられるか？」に Yes と言えること
